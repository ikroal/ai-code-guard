## 1. 引言

架构风格的选择是软件设计中最具长期影响的决策之一。一个错误的架构风格选择不仅增加实现复杂度，更会在系统演化过程中持续产生摩擦——开发者需要不断回答"这个功能应该放在哪一层"这类本不该存在的问题。

AI Guard 是一个面向 AI 编码 Agent 的看护系统，以 CLI 工具的形式提供行为约束与代码质量门禁能力。在其初始设计过程中，曾提出五层分层架构（CLI 层 → 配置层 → 核心层 → Agent 适配层 → 输出层）。本文对这一架构选择进行批判性分析，并基于系统实际数据流特征和业界实践，推导出更为适切的架构风格。

## 2. 架构风格分类与适用域

### 2.1 分层架构（Layered Architecture）

分层架构将系统组织为若干水平层，每层只依赖其下层，请求从最上层穿透至最下层后逐层返回。

**核心假设**：存在一条（或少数几条）贯穿所有层的主请求路径。

**典型适用域**：
- Web 后端服务：HTTP 请求 → Controller → Service → Repository → Database
- 操作系统：应用层 → 系统调用 → 内核 → 硬件抽象

**优势**：依赖方向明确，层间职责清晰，团队可按层分工。

**局限**：当系统存在多条不共享中间层的独立执行路径时，分层模型会制造虚假的依赖关系——某些层对某些路径而言是不必要的穿透。

### 2.2 管道架构（Pipeline Architecture）

管道架构将处理过程组织为线性的阶段序列，数据从一个阶段单向流入下一个阶段。

**核心假设**：数据经过固定的、有序的处理阶段。

**典型适用域**：
- 编译器：Lexer → Parser → AST → Optimizer → CodeGen
- 数据 ETL：Extract → Transform → Load
- Unix 管道：`cat | grep | sort | uniq`

**优势**：阶段间解耦，每个阶段可独立替换或测试。

**局限**：要求数据流严格线性，不适合多入口、多出口或分支处理的场景。

### 2.3 共享模块 + 命令编排（Shared Modules + Command Orchestration）

系统由一组功能内聚的模块组成，每个 CLI 命令作为编排者，按需组合所需模块完成特定任务。模块之间通过明确的接口协作，但不存在预设的层级或流水线顺序。

**核心假设**：系统有多个入口（子命令），每个入口编排不同的模块子集。

**典型适用域**：
- CLI 工具（多子命令）
- 开发者工具（DevTools）
- 插件化系统

**优势**：每条执行路径只引入必要模块，无冗余穿透；新增命令只需编排现有模块，不影响其他命令。

**局限**：缺乏分层架构那样直观的"全局结构图"，需要通过模块依赖图来理解系统结构。

## 3. 分层架构在 CLI/DevTools 中的适用性分析

### 3.1 分层假设的验证

以 AI Guard 初始设计的五层架构为例：

```
CLI 层 → 配置层 → 核心层 → Agent 适配层 → 输出层
```

验证其核心假设——"是否存在贯穿所有层的主请求路径"：

| 执行路径 | CLI | 配置 | 核心(Materializer) | 核心(Enforcer) | 核心(Verifier) | 适配层 | 输出层 |
|---|---|---|---|---|---|---|---|
| `guard install` | ✅ | ✅ | ✅ | ❌ | ❌ | ✅ | ✅ |
| PreToolUse Hook | ❌ | ✅* | ❌ | ✅ | ❌ | ❌** | ✅ |
| `git commit` | ✅ | ✅ | ❌ | ❌ | ✅ | ❌ | ✅ |

> \* 运行时读取的是安装时缓存的配置，非实时解析  
> \*\* Hook 脚本在安装时已生成为 Agent 特定格式，运行时无需适配层

**结论**：三条主要执行路径中，没有任何一条穿透全部五层。每条路径跳过了至少两层。这意味着分层架构的核心假设不成立——五层结构中存在大量"空穿透"。

### 3.2 空穿透的代价

当分层假设不成立时，架构面临两种不良选择：

1. **强制穿透**：让不需要的层实现空转发逻辑，增加代码量和维护负担。
2. **允许跨层调用**：破坏分层纪律，使分层架构名存实亡。

两种选择都在说明同一个问题：分层架构不是此类系统的自然结构。

### 3.3 "适配层"独立性的再审视

原设计将 Agent 适配层独立为一层，理由是"协议转换与核心逻辑分离"。但深入分析可发现：

**安装时**：Agent 差异体现为生成不同格式的文件（CLAUDE.md vs `.cursor/rules/`）。这本质上是生成器（Materializer）的**策略变体**，而非一个需要数据流经过的独立"层"。

**运行时**：每个 Agent 的 Hook 脚本是安装时预生成的，其中已经内嵌了协议转换代码（例如 Claude Code 的 Hook 脚本直接输出 Claude Code 格式的 JSON）。运行时**不存在**一个通用入口动态适配不同 Agent 协议的过程。

**提交验证时**：Git Hook 是 Git 原生机制，与 Agent 类型完全无关。

因此，Agent 适配不是一个运行时的"协议转换层"，而是安装时的**生成策略差异**。将其建模为策略模式（Strategy Pattern）嵌入生成器，比独立为一个架构层更贴合实际。

### 3.4 "输出层"抽象时机的审视

原设计定义了 Content → Renderer → Channel 三级输出管道。此设计的完整形态（支持 Markdown/JSON/HTML 渲染 + 终端/文件/GitHub/Slack 等输出通道）具有合理性，但需要审慎评估引入时机。

在系统早期阶段，输出需求仅为：写文件到磁盘、打印到终端。为尚未实现的 PR 评论、Slack 通知等场景预建三级抽象，存在过早抽象的风险。

更务实的做法是：先以简单的格式化输出模块满足当前需求，当 PR 报告等功能确实进入实现阶段时，再引入 Channel 抽象。**接口的引入应由实际的第二个实现者驱动，而非假想的未来需求。**

## 4. 业界 CLI/DevTools 架构实证

### 4.1 案例分析

**Terraform**（基础设施即代码工具）

Terraform 拥有 `init`、`plan`、`apply`、`destroy` 等多个子命令，每个命令编排不同的内部模块（配置加载、Provider 管理、状态管理、执行引擎）。其架构并非分层，而是以共享核心（配置解析 + Provider 注册 + 状态存储）为基础，各命令按需组合。

**ESLint**（JavaScript 代码检查工具）

ESLint 的架构是典型的管道模式——配置加载 → 规则解析 → 文件遍历 → 规则执行 → 结果汇总 → 格式化输出。但其 CLI 入口和 Node.js API 入口共享相同的管道实现，体现了"多入口 + 共享处理模块"的思想。

**Docker CLI**

Docker CLI 的每个子命令（`build`、`run`、`push`）是独立的命令处理器，共享 API Client 和镜像存储等基础模块。没有层级关系，只有模块依赖关系。

**kubectl**（Kubernetes CLI）

kubectl 采用了 Cobra 命令框架，每个命令是一个独立的 handler 函数。所有命令共享 API Client、配置加载、输出格式化等模块，但各命令的处理逻辑完全独立。

### 4.2 共性归纳

| 特征 | Terraform | ESLint | Docker CLI | kubectl |
|---|---|---|---|---|
| 多子命令 | ✅ | ✅ | ✅ | ✅ |
| 共享配置模块 | ✅ | ✅ | ✅ | ✅ |
| 命令间逻辑独立 | ✅ | 部分 | ✅ | ✅ |
| 严格分层 | ❌ | ❌ | ❌ | ❌ |
| 模块按需组合 | ✅ | ✅ | ✅ | ✅ |

**结论**：业界成熟的 CLI/DevTools 工具普遍采用"共享模块 + 命令编排"模式，而非严格分层架构。这不是偶然选择，而是由此类工具的共同特征——多子命令、各命令编排不同模块子集——所决定的。

## 5. AI Guard 架构的第一性原理推导

### 5.1 从执行路径出发

抛开预设的架构风格，回到 AI Guard 的实际执行路径：

**路径 1：安装（`guard install`）**
```
读取 guard.yaml → 合并配置 → 为每个 Agent 生成规则文档 → 生成 Hook 脚本
→ 生成工具配置 → 生成 .pre-commit-config.yaml → 安装 Git Hooks → 打印摘要
```

**路径 2：运行时拦截（PreToolUse Hook）**
```
从 stdin 读取 JSON → 加载缓存的策略 → 分类工具操作 → 提取匹配目标
→ 执行规则匹配 → 输出判定结果到 stdout
```

**路径 3：提交验证（`git commit`/`git push`）**
```
Git Hook 触发 → 识别阶段（commit/push）→ 委托 pre-commit 执行检查
→ 收集结果 → 格式化报告 → 通过或拦截
```

### 5.2 提取共享与独立部分

三条路径的交集与差集：

| 模块 | 路径 1 | 路径 2 | 路径 3 | 性质 |
|---|---|---|---|---|
| 配置加载与合并 | ✅ | ✅* | ✅ | **共享** |
| 工件生成（规则文档、Hook、工具配置） | ✅ | ❌ | ❌ | 路径 1 专属 |
| Agent 生成策略 | ✅ | ❌ | ❌ | 路径 1 专属 |
| 规则匹配与策略判定 | ❌ | ✅ | ❌ | 路径 2 专属 |
| 检查编排 | ❌ | ❌ | ✅ | 路径 3 专属 |
| 结果格式化与输出 | ✅ | ✅ | ✅ | **共享** |

> \* 路径 2 读取的是安装时生成的配置缓存

### 5.3 推导模块划分

基于上述分析，自然推导出以下模块：

| 模块 | 职责 | 服务的路径 |
|---|---|---|
| **Config** | 配置加载、合并、校验 | 路径 1、2、3 |
| **Generator** | 安装时生成所有工件 | 路径 1 |
| **Enforcer** | 运行时规则匹配与策略判定 | 路径 2 |
| **Checker** | 提交时检查编排 | 路径 3 |
| **Reporter** | 结果格式化与多渠道输出 | 路径 1、2、3 |
| **CLI** | 命令解析与编排 | 路径 1、3 |

Agent 适配作为 Generator 内部的策略模式存在，不作为独立模块。

### 5.4 模块依赖关系

```
CLI ──→ Generator ──→ Config
 │                  ↗
 ├──→ Checker ────
 │                  ↘
 └──→ Reporter       (独立使用)

Enforcer ──→ Config (独立入口，由 Hook 脚本触发)
         ──→ Reporter
```

关键约束：
- **无循环依赖**：依赖方向单向
- **Config 是共享基础**：所有业务模块依赖 Config
- **Enforcer 独立入口**：不经过 CLI，由外部 Hook 脚本直接调用
- **Reporter 是横切关注点**：被多个模块使用，但不依赖任何业务模块

## 6. 设计原则的实践应用与权衡

### 6.1 YAGNI 原则（You Aren't Gonna Need It）

**含义**：不为尚无实际需求的功能预建抽象。

**在本案例中的应用**：

原设计中的 Content → Renderer → Channel 三级输出管道是一个典型的 YAGNI 风险点。在系统仅需写文件和打印终端的阶段，三级抽象增加了概念负担而无实际收益。

**但 YAGNI 需与前瞻性平衡**：当某个抽象点的引入成本随时间急剧增长时（例如到处硬编码了 `print()` 调用），适当的早期抽象是合理的。判断标准是：**引入抽象的驱动力应是已确认的第二个实现者，而非假想的未来需求。**

### 6.2 开闭原则（Open-Closed Principle）

**含义**：对扩展开放，对修改关闭。

**在本案例中的应用**：

Agent 适配是开闭原则的典型应用场景。新增 Agent 时应只需添加新的适配器，不修改现有代码。原设计将适配层独立为一个架构层来强化这一点。

**反思**：开闭原则可以通过多种机制实现——独立的架构层只是其中之一。策略模式、注册机制、插件系统同样能满足开闭原则，且无需引入额外的架构层级。**原则是目标，模式是手段，不应将手段与目标混淆。**

### 6.3 关注点分离（Separation of Concerns）

**含义**：不同的职责应由不同的模块承担。

**在本案例中的应用**：

原设计的关注点分离体现在"配置层不做判定、核心层不做配置解析、适配层不做策略逻辑"。这些边界约束是合理的。

**但关注点分离不等于层级分离**：将不同关注点放在不同模块中（模块级分离）就已满足原则要求。将其进一步提升为不同架构层（层级分离）是一种更强的约束，只有在确实存在层间契约需求时才是必要的。

### 6.4 Fail-Closed 原则

**含义**：系统异常时采取安全的默认行为（拒绝而非放行）。

**在本案例中的应用**：

对于行为约束系统，fail-closed 不是可选项而是必需品。当 Hook 脚本崩溃、配置缺失、Pattern 匹配异常时，系统应默认拒绝操作，而非默认放行。

此原则影响架构设计：Enforcer 模块的错误处理路径必须是 deny，且该行为不可被配置覆盖。这是**安全性约束优先于可用性约束**的体现。

## 7. 推荐架构：共享模块 + 命令编排

### 7.1 架构总览

```
┌─────────────────────────────────────────────────────────┐
│                     CLI (命令入口)                        │
│  ┌──────┐ ┌───────┐ ┌───────┐ ┌──────┐ ┌───────┐       │
│  │ init │ │install│ │ check │ │verify│ │status │ ...    │
│  └──┬───┘ └──┬────┘ └──┬────┘ └──┬───┘ └──┬────┘       │
│     │        │         │         │        │             │
└─────┼────────┼─────────┼─────────┼────────┼─────────────┘
      │        │         │         │        │
      ▼        ▼         ▼         ▼        ▼
┌──────────────────────────────────────────────────────┐
│                   业务模块                              │
│                                                       │
│  ┌───────────┐  ┌──────────┐  ┌──────────┐           │
│  │ Generator │  │ Enforcer │  │ Checker  │           │
│  │ (工件生成) │  │ (行为判定)│  │ (检查编排)│           │
│  └─────┬─────┘  └─────┬────┘  └─────┬────┘           │
│        │              │             │                 │
│        │  ┌───────────┴──────┐      │                 │
│        └─→│ AgentAdapter     │      │                 │
│           │ (Agent生成策略)   │      │                 │
│           └──────────────────┘      │                 │
└────────┬──────────────┬─────────────┴─────────────────┘
         │              │
         ▼              ▼
┌──────────────────────────────────────────────────────┐
│                   基础模块                              │
│                                                       │
│  ┌──────────┐              ┌──────────┐               │
│  │  Config  │              │ Reporter │               │
│  │ (配置管理)│              │ (结果输出)│               │
│  └──────────┘              └──────────┘               │
└──────────────────────────────────────────────────────┘
```

### 7.2 命令编排示例

每个 CLI 命令是一个编排函数，按需组合模块：

```
install 命令:
  config = Config.load("guard.yaml")
  adapter = AgentAdapter.get(agent_type)
  artifacts = Generator.generate(config, adapter)
  Generator.write(artifacts)
  Reporter.print_summary(artifacts)

PreToolUse Hook (非 CLI 入口):
  policy = Config.load_cached()
  tool_call = parse_stdin()
  decision = Enforcer.evaluate(tool_call, policy)
  Reporter.write_stdout(decision)

check 命令:
  config = Config.load("guard.yaml")
  files = get_staged_files()
  report = Checker.run(config, files, stage="commit")
  Reporter.print_report(report)
```

### 7.3 与原五层架构的对比

| 维度 | 五层分层架构 | 共享模块 + 命令编排 |
|---|---|---|
| 结构直觉 | 直观的层级图 | 需通过依赖图理解 |
| 空穿透 | 存在（多条路径跳过中间层） | 不存在（只引入需要的模块） |
| 新增命令 | 需决定"属于哪一层" | 直接编排已有模块 |
| 新增 Agent | 需在适配层添加实现 | 在 AgentAdapter 注册新策略 |
| 模块间耦合 | 受层级约束（只能依赖下层） | 受依赖方向约束（无循环依赖） |
| 概念负担 | 5 层 + 层间契约 | 6 个模块 + 依赖规则 |

## 8. 结论

1. **分层架构并非 CLI/DevTools 的自然结构**。当系统存在多条不共享中间层的独立执行路径时，分层架构会引入空穿透，增加无谓的概念复杂度。

2. **业界 CLI 工具普遍采用"共享模块 + 命令编排"模式**。Terraform、Docker、kubectl 等成熟工具的实践验证了这一点。

3. **架构应从实际数据流推导，而非从预设模式套用**。通过分析 AI Guard 的三条独立执行路径（安装、运行时、提交验证），自然推导出 6 个功能模块的划分，比预设"五层"更贴合系统真实结构。

4. **设计原则是目标，架构模式是手段**。开闭原则可以通过策略模式实现，不必以独立架构层为代价；关注点分离可以在模块级完成，不必提升为层级分离。

5. **抽象的引入应由实际需求驱动**。Content → Renderer → Channel 等精细抽象应在具备第二个实现者时引入，而非基于假想的未来需求预建。
